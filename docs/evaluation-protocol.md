# Skill 评测与迭代协议

状态：v0.1 设计草案。这里的约束决定成绩是否可解释，优先于报告展示或自动优化速度。

## 1. 测评对象与三种模式

| 模式 | 操作方式 | 回答的问题 |
| --- | --- | --- |
| controlled | 固定方式显式提供目标 Skill，记录注入位置/加载证据 | 在这个执行环境中，提供 Skill 是否改善任务表现？ |
| native | 按平台原生方式安装，任务提示不点名 Skill | 平台能否正确发现、触发并使用它？ |
| coexistence | 在冻结的其他 Skill 集合中添加目标 Skill | 共存时是否误触发、冲突或相互影响？ |

v0.1 优先实现 controlled。明确区分 `prompt-inline`、`explicit-file-read` 等加载方法，并写入可比性指纹。正文已放进提示不等于模型遵循了它；要求模型读文件也不能当成已经成功读取。

controlled 中未加载的尝试仍保留，单独报告加载失败。原始分析保留所有有效执行尝试；“仅成功加载的任务”的比较只作辅助，避免通过筛掉失败任务抬高效果。缺少加载观测时使用 unknown。

native 增加应触发、相似但不应触发、完全无关三类任务，单独报告触发精确率/召回率和任务成功率。触发不易观测的平台不能宣称这个维度已测量。

## 2. 对照矩阵

每个执行 Profile 内，固定模型、平台版本、工具、环境、配置、任务、预算、加载方式和重复次数，只改变目标 Skill：

- none：没有目标 Skill，其他公共内容不变。
- incumbent：当前版本。
- candidate：候选版本。

“无 Skill”默认意为无目标 Skill。平台不可禁用的内建能力应如实列出；报告不能声称所有平台背景指令都相同。

定义：Skill 增益 = 当前版本 − none；迭代增益 = candidate − incumbent。

优先在每个 Profile 内比较增益。不同平台搭配不同模型时，其绝对分数同时受模型和 Agent 运行框架影响，不能归因于平台本身。跨平台结论须列出实际测试矩阵和未支持项。

## 3. Suite 与数据边界

每个 Suite 提供公开任务输入、冻结环境、隐藏期望/评分器、任务族 ID 和数据来源。AI 可以辅助起草任务和 rubric；这些在运行前冻结，不能由候选 Skill 自己定义通过条件。

| 数据 | 被测 Agent 可见 | 迭代器可见 | 用途 |
| --- | --- | --- | --- |
| train 输入 | 当前题公开输入 | 是 | 诊断与形成修改假设 |
| train 评分、轨迹 | 不作为同次任务提示 | 是 | Wiki 与候选生成 |
| validation 输入 | 当前题公开输入 | 否 | 开发期门禁 |
| validation 结果 | 不作为同次任务提示 | 聚合摘要、接受/拒绝 | 选择候选 |
| test 输入 | 测试时仅当前题公开输入 | 否 | 冻结版本后的最终审计 |
| test 评分、轨迹 | 否 | 否 | 交给实验拥有者的最终报告 |

train / validation / test 按任务族、仓库、模板等来源分组切分，避免同一题的近似变体跨集合。`regression` 是 validation 内预先标注的任务子集，可跨多个能力族，不是默认额外重复计入总分的第四份数据。导入独立回归集时也要去重并明确权重。

验证反馈属于开发信号，重复使用会造成过拟合。每次演化会话预先设定候选数、轮次、预算和停止规则；不能不断试到“显著”为止。开发集统计不当作最终泛化证明。

最终 test 只对冻结候选做预先定义的一次审计批次，批次内可包含预先设定的多次重复。如果利用测试结论继续改 Skill，这份测试集应标记为已暴露，后续正式审计使用新的未见集合。

## 4. 单题执行

1. 从固定快照准备公开任务环境，不挂载答案、其他条件输出或 Wiki。
2. 创建全新会话，配置预算，按条件注入目标 Skill。
3. 捕获平台公开事件、调用结果、可用用量和最终产物。
4. 完成或达到预算后停止，保存终态；LLM 声称“完成”不等于通过。
5. 在独立评分环境运行已冻结的 Grader，生成结构化证据。

任务执行失败、模型输出无效、模型耗尽工具/时间预算：计入任务失败。平台限流、网络基础设施中断、镜像拉取失败：记为 infrastructure error，按预先设定的策略重试。评分器崩溃：grader error。不能用静默重试挑选成功样本。

每个计划项固定重复编号；基础设施重试只是该编号下的新 attempt，不是额外独立样本。超过重试上限的缺失配对单独展示，超过预设阈值则比较结论为 inconclusive。

## 5. 评分规则

以 Suite 的真实产物为主要依据：测试、数值断言、文件差异、结构校验等。没有可靠自动判定的任务，使用版本化 rubric 和盲评；固定评审模型及配置，并抽样校准评审一致性。

评分器不读取条件名称、Wiki 假设或候选解释，尽量只接收完成判断所需的任务与产物。运行产物可能含提示注入，模型评审将其当数据处理，不授予工具执行权。

推荐分开报告：

| 指标 | 定义 |
| --- | --- |
| 主成功率 | 所有指定硬条件同时通过的有效 Trial 比例 |
| 质量分 | Suite 指定的有锚点分数；与成功率分别报告 |
| 回归率 | incumbent 成功而 candidate 失败的配对次数 / incumbent 成功的配对次数 |
| 关键回归 | Suite 标记的关键任务/断言出现退化的明细 |
| 成本 | 输入/输出/缓存 Token、已报告费用、独立估算费用 |
| 时延 | p50/p95、超时率；标注端到端时长和模型执行时长 |
| 工具行为 | 调用错误、预算耗尽、加载和规则遵循的观测证据 |
| 数据质量 | 基础设施失败、评分器错误、缺失率、观测覆盖度 |

无法观测的指标为 null/unknown，不能填 0。包月账号的现金成本不能直接等同于 Token 估算价。增加回归测试数量只是过程证据，不能替代隐藏测试成功率。

## 6. 重复、配对与不确定性

每题每条件默认做 3 次独立新会话作为初始开发配置，顺序按任务和重复编号随机交错。模型不支持 seed 时记录“不支持”；调度随机种子不伪装成模型随机种子。

同一任务的多次尝试有关联。比较时先计算每题各条件的平均分及差值，再按任务聚类 bootstrap；存在共享来源的任务则按更高层的来源组重采样。Suite 类别权重与多 Profile 权重在实验前固定。

报告点估计、95% 区间、样本/任务族数量、每题差异和逐类退化。重复 3 次不保证检出小幅增益；低样本或宽区间时使用 inconclusive。未来支持 pass@k 时必须同时明确尝试预算和估计方式，不能把基础设施重试算作 pass@k。

## 7. 门禁策略

门禁输出：`accept`、`reject`、`inconclusive`。`accept` 表示符合该比较的开发准入政策；需要正式发布的版本还应满足声明的测试审计要求。

以下是演示默认值，需在实际 Suite 上校准，所有阈值在运行前写入 policy 快照：

| 条件 | 示例政策 |
| --- | --- |
| 迭代增益 | candidate − incumbent ≥ 0.03，且 95% 区间下界 > 0 |
| 相对 none | candidate − none 的区间下界 ≥ −0.02 |
| 关键回归 | 0 个预定义关键失败 |
| 普通回归 | 回归率单侧 95% 上界 ≤ Suite 允许的上限 |
| 成本 | 若声明成本约束，则可观测且平均 Token 比率 ≤ 1.20 |
| 数据质量 | 缺失配对 ≤ 5%；无产物/评分器完整性问题 |
| 比较完整 | 预设矩阵已完成；不能因某平台退化而临时剔除它 |

明确违反硬限制或有充分证据表明退化则 reject；区间太宽、必要指标缺失或可比性不足则 inconclusive。只有完整满足政策时 accept。低样本“零回归”不等于已证明低回归风险。

本设计不在测试以后调整阈值来接纳候选，也不将一次随机的小幅下降直接认定为退化。

## 8. 演化策略

每轮只修改一个目标 Skill；允许它的正文、description、脚本和资源发生变化，必须完整记录 diff 和父快照。v0.1 默认限制为文档修改，脚本演化作为后续能力。

Wiki Maintainer 的输入是训练证据与历史开发决策。输出包括观察、可能原因、反例、适用任务族、平台/模型限制。Proposer 提出一个可证伪的假设、预期改善指标和候选 diff。

同样的失败也可能来自任务歧义、环境或评分器错误。必须先分类；确认属于评测系统缺陷时修正 Suite/Grader 版本并重跑对照，不能把它写成 Skill 必须遵守的新规则。

每轮流程：训练 → Wiki 更新 → 候选 → 完整性检查 → validation/回归 → Gate → 追加 Ledger。通过则更新会话内 incumbent，未通过则保留旧版本；达到预算、最大轮数或连续无改善次数时停止。

跨平台共享的候选必须通过声明矩阵的检查。某平台专属补丁可以独立分支并注明适用范围，不能在共享 Skill 中悄悄添加针对某模型的限制。
